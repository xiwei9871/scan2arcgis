# 03 核心阻塞问题与根因分析

本文件回答：为什么投入约 8 个月、171 个提交、约 13 万行代码（含测试），项目仍没有一个可交付的端到端结果。

## 1. 结论摘要

| 排名 | 根本原因 | 置信度 |
|---|---|---|
| R1 | 没有定义"正确结果"和"可交付质量"。评估集只有 2 张图、十几个局部标注，门槛贴着现有结果设定，2026-06 以后不再运行评估。开发靠人工看图发现问题、再加规则修补。 | VERIFIED（事实）/ INFERRED（因果） |
| R2 | 把研究型问题（无监督地从扫描地质图中提取线、面、点符号）当作普通功能开发处理，用手工阈值规则逐个修补，没有可泛化的方法，也没有可行性验证阶段。 | INFERRED（证据充分） |
| R3 | 没有 MVP 边界。核心问题未解决时持续扩展范围（侵入岩、矿种、ML、MoE、断层）并多次全系统重构字段契约，消耗开发量，同时破坏测试保护。 | VERIFIED（事实）/ INFERRED（因果） |

"代码质量差"不是根因。代码组织确有问题（15,000 行的路由文件），但即使代码整洁，R1–R3 依然会让项目停滞。

## 2. 根因分析树

### 树 1：地质界线始终达不到可用

| 层级 | 内容 |
|---|---|
| Symptom | 33 个提交修改界线模块；图框/经纬网误检、近色漏检、断点连线、坐标偏移反复出现（见 02 文档 4.1） |
| Immediate Cause | 每次修复都是针对某张图某个区域加规则或阈值；`boundary/` 12,061 行中有 1,410 个浮点字面量；规则之间相互影响（例如 `33e5f7b` 要"统一执行过滤，减少特殊保留路径绕过检查"，说明此前已有多条绕过路径） |
| Root Cause | (a) 缺少足够的标注数据来衡量改动是变好还是变坏（R1）；(b) 方法选择：纯传统 CV 启发式，没有用"图例驱动的有监督或交互式分割"这类在同类问题上验证过的方法（R2） |
| Evidence | baseline 界线 `buffer_f1=0.1222`（E13）；评估最后一次入库是 06-01；10 月仍在修同类误检（`953b405`、`33e5f7b`） |
| Proposed Validation | 用 20–30 张真实图幅、全幅标注建立评估集；对当前代码跑一次，得到真实 F1；与 DARPA AI4CMA 公开数据上的已知方法对比（见 05 文档） |

### 树 2：测试失去保护作用

| 层级 | 内容 |
|---|---|
| Symptom | 245/1,148 个测试失败；Linux 下 42 个测试文件无法导入 |
| Immediate Cause | 字段改名（`symbol_shape_id`→`symbol_shape_key`、`section_id`、`region_id`→`region_key`）、删除 `contour_pipeline` 属性后，测试未同步；Windows-only `msvcrt` 导入；`matplotlib` 未声明 |
| Root Cause | 无 CI，无"测试必须通过"的提交约束；只在一台 Windows 机器上运行；测试被 `.gitignore` 忽略后强制加入，入库是被动的 |
| Evidence | E09、E10；GitLab 无 pipeline |
| Proposed Validation | 在干净的 Linux 和 Windows 环境中各跑一次；加最小 CI 后观察一周内的失败率 |

### 树 3：等高线功能失败并被停用

| 层级 | 内容 |
|---|---|
| Symptom | 10-15 停用；baseline `elevation_accuracy=0.0`，碎片率 1.0 |
| Immediate Cause | 高程注记 OCR 与线条关联未成功；等高线与地质界线、格网颜色混淆 |
| Root Cause | 等高线在地质图上通常是浅色细线，与其他线要素交织，传统颜色分割难以分离；没有先做可行性验证就作为核心功能开发（R2） |
| Evidence | E06、E13 |
| Proposed Validation | 如业务确实需要等高线，应先确认能否从测绘部门获取 DEM 或数字地形图，从而完全避免矢量化 |

### 树 4：开发量被非核心功能占用

| 层级 | 内容 |
|---|---|
| Symptom | ML 样本库、训练、模型发布、MoE 专家注册/路由/影子运行/晋级/回滚等约 1 万行代码，外加大量前端 |
| Immediate Cause | 在基线识别质量未达标时建设 ML 运维基础设施 |
| Root Cause | 没有 MVP 边界和 Go/No-Go 门槛（R3）；[HYPOTHESIS] 可能期望"积累样本后自动变好"，但没有训练出可证明有效的模型 |
| Evidence | MoE 文档写明"只生成候选结果，不改变生产结果"；YOLO adapter 只做数据格式转换，仓库中没有检测模型；Git 历史中约 1.5 GB 影子运行 JSON |
| Proposed Validation | 统计每个已发布 ML 模型在留出数据上相对基线的提升；若无法统计，视为没有价值 |

### 树 5：无法部署到客户环境

| 层级 | 内容 |
|---|---|
| Symptom | Docker 配置与依赖版本冲突；GDAL 依靠 Windows wheel；`.venv` 入库 |
| Immediate Cause | 只在开发机上运行 |
| Root Cause | 从未有过一次面向客户环境的交付演练（R3 的工程侧表现） |
| Evidence | 01 文档第 6 节 |
| Proposed Validation | 在一台干净机器上按文档安装，记录需要几步、哪里失败 |

## 3. 对任务书第 B3 节各问题的逐项回答

| 问题 | 回答 | 标签 |
|---|---|---|
| 需求定义是否存在根本问题？ | 是。没有书面的精度要求、交付格式要求、要素范围；设计文档有空白条目（核心功能第 4 项为空）；范围随开发不断变化 | VERIFIED |
| 是否把研究型算法问题当成普通开发？ | 是。没有可行性研究阶段；第一个月就同时开发三个识别模块和全套 UI | INFERRED |
| 是否缺少真实数据集和评估标准？ | 是。仓库中仅 2 张完整地质图；标注为 "draft_partial_label"，界线标注共 5 条线 | VERIFIED |
| 是否过早追求全自动化？ | 部分是。设计目标"尽量全自动"；但后期已加入图例人工录入和补识别，方向在改善 | VERIFIED |
| 是否存在不现实的精度预期？ | UNKNOWN。没有书面精度要求。公开文献中，即使有用户提示，线要素的中位 F1 也只有约 0.56（见 05 文档），这是需要向业务方说明的现实 | UNKNOWN |
| 是否选择了不合适的算法？ | 对线、点要素，手工阈值方法难以泛化（INFERRED）；对配准，自研求解器重复了 GDAL 已有功能（VERIFIED） | 混合 |
| 是否过度依赖难以稳定运行的环节？ | 是。PaddleOCR 用于角点坐标和图例；GDAL 只能在 Windows 上装 | VERIFIED |
| 是否通过补丁掩盖架构问题？ | 是。见树 1 | INFERRED |
| 是否缺少端到端验收？ | 是。唯一的端到端记录 `reports/validation/frontend_full_acceptance_20260913.json` 验证的是流程能走通（按钮、计数、发布/恢复），不是输出是否正确；全分辨率端到端测试在审计环境 178 秒内未完成 | VERIFIED |
| 是否缺少 MVP 边界？ | 是 | VERIFIED |
