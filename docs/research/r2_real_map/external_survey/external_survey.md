# 外部开源项目源码调研（2026-10-28）

本轮只读源码、做判断，不集成任何代码，不改动 R1/R2 的评价标准。
源码快照（commit 和日期）见 `repos_snapshot.json`。仓库克隆在本地临时目录，没有进入本仓库。

起点文章（四川德格地质图在线地图）只做了扫描图配准、切瓦片和网页浏览，没有自动识别或矢量化，所以本轮不把它当作技术参考。

## 1. 结论摘要

| 项目 | 许可证 | 实际能力 | 能否直接复用 | 对我们的价值 |
|---|---|---|---|---|
| MapReader | MIT（文字识别依赖的模型为**非商用**） | 大图切块，块级 CNN 分类，文字检测与识别 | 只有切块逻辑可复用 | 低到中：适合大图分块和块级粗筛；文字识别模型不能商用 |
| Geology from points and lines | GPL-3.0 | 人工矢量化的界线和标注点 → 闭合成面 → 按点赋地层属性 | 不复用代码（GPL，且依赖 QGIS） | 中：验证了路线 A 的后半段设计，并给出一个可用的质检规则 |
| AutoTracer | **无许可证文件**（默认保留所有权利） | 二值化 → 骨架化 → 追踪成折线 | 不能复用代码 | 低：方法是标准做法，可以自己独立实现，作为墨线检测基线 |
| Raster Vectorizer | GPL-2.0 | 人工选 HSV 颜色范围 → 面 | 不复用 | 很低：相当于手动版的最近颜色分类 |
| Allmaps | 大部分为 MIT；部分包为 GPL-3.0 / AGPL-3.0 | IIIF 地图配准与叠加浏览 | 留作产品参考 | 只与后续产品能力相关 |
| Map Warper | MIT | Rails + GDAL 的配准、校正与切瓦片服务 | 留作产品参考 | 只与后续产品能力相关 |

**总体判断：** 这些项目都没有解决我们诊断出的核心瓶颈，也就是"系统自己判断每块区域属于哪个地层"（语义准确率为 0）。
能借鉴的是方法和设计思路，不是可以直接拿来用的模块。

## 2. MapReader（maps-as-data/MapReader，MIT）

**源码结构：** `mapreader/` 下有 `download`、`load`、`annotate`、`classify`、`process`、`spot_text` 几个模块。

- **切块（`load/images.py`）：** `patchify_all()` 支持按像素或按地面距离切块，参数有 `patch_size`、`overlap`、`square_cuts`，并记录每块在父图中的坐标。这部分逻辑清晰，不依赖深度学习框架。
- **分类（`classify/classifier.py`）：** 整块分类。基于 torchvision/timm 预训练模型做迁移学习，一块图输出一个标签，例如"有铁路 / 无铁路"。训练前需要**人工标注大量图块**（`annotate` 模块提供标注界面）。输出是网格，分辨率等于块的大小，不是像素精度的多边形。
- **文字识别（`spot_text/`）：** 三个运行器，背后分别是 DeepSolo、DPText-DETR、MapTextPipeline，都基于 detectron2。
  - detectron2 本身是 Apache-2.0。
  - 三个模型仓库（`maps-as-data/DeepSolo`、`maps-as-data/DPText-DETR`、`yyyyyxie/MapTextPipeline`）的 LICENSE 开头都是 "AdelaiDet for non-commercial purposes (For commercial use, contact ...)"。**商业使用需要另行取得授权。**
  - 权重文件（文档示例中的 `art_final.pth`、`rumsey-finetune.pth`）需要单独下载，许可条款本轮没有核实。
  - 文档示例用的是 `device="cuda"`。Mac 上能否运行（CPU 或 MPS）本轮没有测试。
- **后处理（`process/`）：** 只有遮挡分析等解释性工具，没有线条矢量化、拓扑重建，也没有图例属性关联。

**适用性：** MapReader 是为英国历史地形图设计的，典型任务是"这一块有没有铁路或建筑"，没有地质图的用例。它的块级分类粒度太粗，表达不了小地质单元和细长地层带，而我们的诊断显示，小实例召回只有 0.24–0.41，正是现在的弱项。

**人工输入：** 训练分类器需要人工标注图块；文字识别用预训练模型，可以自动运行。

**集成：** 它是纯 Python 包，可以作为库调用。但依赖 torch、torchvision、timm，文字识别还需要从源码编译 detectron2，依赖很重。
如果只用切块，自己写或照搬几十行代码（保留 MIT 声明）比引入整个包更合适。

**值得验证的新方法：**
1. 带重叠的切块加块级推理：将来处理 gm1 这种 1.9 万像素的大图时用得上。R1 目前是整图缩到一半处理。
2. 地图文字检测模型。MapTextPipeline 是针对历史地图训练的，对弯曲、旋转的地名标注效果较好。但它面向地名，不是地层代号（如 `t1`、`Ohf`）；而且有非商用限制，不能进入产品路线。只能作为研究对照，验证"地图专用文字检测"比通用 OCR 好多少。

## 3. Geology from points and lines（pinogcosentino，GPL-3.0）

**源码结构：** 一个 QGIS Processing 插件。核心是 `G4PL_algorithm.py`（1385 行），另有 `data/` 下的 QGIS 图形化模型文件。

**流程（按调用的 QGIS 算法顺序）：**
1. 输入：已经矢量化的地质界线（线图层），以及带岩性、年代等属性的标注点（点图层）。
2. 线清理：`native:explodelines`（拆成线段）、`native:deleteduplicategeometries`（删重复几何）、`native:removeduplicatevertices`（删重复顶点）。
3. 闭合成面：`native:polygonize`，用线围成面。
4. 属性关联：`native:joinattributesbylocation`，按"点落在面内"把属性赋给面，可选包含、在内部、重叠等空间关系。
5. `native:dissolve`、`native:multiparttosingleparts` 整理输出，同时保留中间结果（面、清理后的点、线段）。

**适用性：** 它是专门为地质图做的，但它的输入是**人工数字化好的线和点**，不处理图像。
它解决的是"线 → 面 → 属性"这一步的拓扑和属性赋值，正好是路线 A 的后半段。

**人工输入：** 界线和标注点都要人工提供。如果把它们换成我们自动识别出的墨线和代号 OCR 结果，就能形成一条全自动的路线 A。

**集成：** 它依赖 QGIS 运行环境，加上 GPL-3.0，不适合直接嵌入我们的 Python 流水线，也会给商业分发带来 GPL 传染问题。
但它的算法本身很简单，用 shapely 的 `polygonize` 加点在面内的空间关联，我们可以独立实现，不需要参考它的代码。

**值得验证的新方法：**
1. **"标注点 → 面"的属性关联方式。** 把图面代号 OCR 的结果当作标注点，按点落在哪个面来赋予地层属性。这和我们诊断结论里的"语义优先"方向完全一致，而且不依赖颜色。
2. **一个现成的质检规则：** 一个面里有 0 个标注点，说明缺代号或者线没有闭合；一个面里有 2 个以上代号不同的标注点，说明少了一条界线，或者某条界线有断口。这两类都可以直接当作自动复核的错误区域，对应 R2-D。

## 4. AutoTracer（Pradipkraze/autotracer，无许可证）

**许可证：** 仓库里没有 LICENSE 文件，README 和 `metadata.txt` 也都没有写许可证。按 GitHub 的默认规则，这意味着保留所有权利，**我们不能复制或修改它的代码**。我们只记录它用了什么方法。

**源码结构：** 一个 QGIS 插件，约 1000 行，核心在 `processing.py`（277 行）。

**流程：**
1. 二值化：Otsu、自适应阈值或手动阈值。
2. 中值滤波平滑。
3. `skimage.morphology.skeletonize` 骨架化。
4. 把骨架当作图来处理：先找端点和交叉点，再沿像素链追踪成折线，丢掉长度小于 `min_contour_length` 的短线。
5. 用 QGIS 写出线图层，按源栅格的地理变换转成地图坐标。

**适用性：** 这套方法对所有暗色像素一视同仁，不区分地质界线、等高线、文字、花纹和断层符号。
我们的诊断里，08001 图面上墨线占 14%，主要是等高线和花纹，08004 只占 0.95%。直接用它，在 08001 上会产生大量假界线。
它也没有拓扑处理：断口不会接上，线不会闭合，交叉点也不会对齐。

**人工输入：** 阈值和最短线长需要人工调。调好之后可以自动运行。

**集成：** 骨架化和图追踪可以用 scikit-image（BSD 许可）和我们自己的代码独立实现，几十行就够。

**值得验证的新方法：** 方法本身不新。但"墨线骨架 → 追踪成线"可以作为我们自己的**墨线检测基线**，用来回答路线 A 和路线 B 都要依赖的一个问题：在 GSJ 图上，单靠黑色墨线能找回多少官方界线？

## 5. 其余三个项目

- **Raster Vectorizer（GPL-2.0）：** QGIS 插件。用户交互式选 HSV 颜色范围，然后提取面并简化。本质上是人工版的最近颜色分类，比 R1 的自动图例分类弱，没有新方法。
- **Allmaps：** 基于 IIIF 的地图配准和网页叠加浏览，前端是 TypeScript。大部分包是 MIT，`packages/db` 和 `packages/api-shared` 是 AGPL-3.0，另有 6 个包是 GPL-3.0。可以作为后续"原图与矢量成果叠加浏览"的参考，使用时要避开 AGPL 和 GPL 的部分。
- **Map Warper（MIT）：** Ruby on Rails 加 GDAL 的配准、校正和切瓦片服务，可以导出 GeoTIFF、WMS、瓦片和 KML。可以作为后续"瓦片浏览"的参考。

这三个项目都不涉及自动识别。

## 6. 路线比较

**路线 A：** 独立检测地质界线 → 用线闭合成面 → 对每个面分类。
**路线 B：** 保留现有面分类 → 独立识别墨线 → 线面融合，修复两者冲突。

下表结合了已有的诊断数据：

| 维度 | 路线 A | 路线 B |
|---|---|---|
| 拓扑 | 由线闭合成面，邻接关系天然一致 | 需要额外做吸附、切分和修复 |
| 小单元 | 线找到了，小单元就能保住（现在小实例召回只有 0.24–0.41） | 依然依赖颜色分类，提升有限 |
| 对墨线质量的敏感度 | **非常高**。一个断口就会把两个单元合成一个；等高线和花纹会产生大量假面（08001 墨线占 14%） | 低。墨线只用来修正，缺失时退回到颜色结果 |
| 没有墨线的界线 | 无法处理（很多中国图只用颜色区分单元） | 可以处理 |
| 理论上限 | 线完美时，等于"理想区域 + 投票"：mIoU 0.60 / 0.48（区域上限口径） | 低于 A 的上限，但更稳定 |
| 对语义瓶颈的作用 | 和"标注点 → 面"天然配合：每个闭合面放代号点 | 也能配合，但区域边界不稳定，一个代号点容易落到错误的面里 |
| 错误定位 | 0 个或多个代号点的面，可以直接列为复核项 | 线和面不一致的位置，可以直接列为复核项 |
| 实施风险 | 高，需要先做好界线专用检测 | 低，可以逐步改进 |

**判断：**

- **主线走路线 B，同时引入路线 A 的"线切分面"作为局部手段。** 只在墨线可信的地方（长、连续、和颜色变化方向一致），用线去切开被错误合并的面、吸附边界；墨线不可信的地方，保留颜色分类的结果。
- **原因：** 路线 A 的上限更高，但对墨线质量要求太严。08001 墨线占图面 14%，等高线和花纹很多，直接闭合成面风险很大。路线 B 能逐步改进，失败时也不会比现在更差。
- **长期方向：** 当训练出一个只响应地质界线、不响应等高线和文字的专用检测器后，路线 A 会变得可行。GSJ 有上千幅带官方矢量的图幅，正好可以作为这种检测器的训练数据。这件事本轮不做。
- **优先级不变：** 无论走哪条路线，都**不能**解决语义准确率为 0 的问题。上一轮"语义优先"的结论仍然成立。线面工作排在代号语义之后，或者在成本很低时并行做。

## 7. 最小对照实验建议（待批准，本轮不实施）

只用开发图 08004 和 08001，评价代码和指标定义完全不变，不打开封存的验收图。

| 编号 | 方案 | 要回答的问题 |
|---|---|---|
| L0 | 墨线检测器单独评价：自己实现的骨架化追踪，对照官方 `geo_L`，算精度和召回（容差和现有线指标一致） | 单靠墨线，能找回多少官方界线？等高线等假线有多少？ |
| A-oracle | 官方 `geo_L` 加图廓 → 闭合成面 → R1 投票 | 路线 A 的上限。应和已有的"理想区域 + 投票"（0.60 / 0.48）一致，用来核对流程 |
| A1 | L0 检测出的墨线 → 闭合成面 → R1 投票 | 线不完美时，路线 A 实际能得多少？ |
| B1 | R1 的面边界吸附到 3 px 内的墨线；被长墨线贯穿的面一分为二 | 路线 B 的增益和风险 |

**统一报告：** 区域上限 mIoU、接触线 F1、实例召回、小实例召回、每个实例被切成的块数，再加上每种方案生成的复核项数量。
**判定规则：** A1 或 B1 相对 R1 的提升，必须超过配准扰动造成的波动（mIoU ±0.008，接触线 F1 ±0.023）才算有效。
**估计工作量：** L0 加 A1 加 B1，约 1–2 天，不需要新增依赖（scikit-image、shapely、rasterio 已在环境里）。
