# 绣娘 3.0：Legend 重绘与 PS 式智能编辑器技术路线讨论

性质：只读研究和讨论，没有修改 B2c、M2、Editor V0.1，没有训练、没有重构、没有部署。
仓库：`xiwei9871/scan2arcgis`，分支 `research/stitchvector-editor-roadmap`，从 `feature/stitchvector-editor-v01 @ 5019ce4` 分出。
PhotoCraft：`storytold/photocraft` 提交 `1f984bf`，只克隆到本地临时目录阅读源码，没有编译或运行。

文中每个判断标明证据等级：
- **【已证明】**：本仓库代码或实测数据证明过
- **【PhotoCraft 有，未验证可移植】**：读了源码，但没有在绣娘里跑过
- **【设想】**：只是设计，尚无实现

## 0. 结论

1. **同意路线方向：保留 StitchVector 3.0 产生几何，下一阶段把重点放在 Legend 重绘和编辑器上。** 但有一处不同意见，见第 1 节第 2 条：碎面问题在 B2c 上已经主要不是"线条笔画污染面层"。
2. **PhotoCraft 适合借鉴设计，不适合 Fork，只有少数小模块值得考虑移植。** 它的选区、画笔、图案都工作在像素栅格上，绣娘的结果是带拓扑的矢量面。真正要自己开发的那一层（画笔意图 → 选中矢量对象 → 几何或样式命令），PhotoCraft 里没有对应物。
3. **推荐路线 A**：保留 Python + Shapely + GPKG 核心和现有网页编辑器，按 PhotoCraft 的交互思路补功能。Rust 只在出现明确性能瓶颈时再考虑，而且优先考虑 Shapely 自身的向量化，而不是引入 Rust。
4. **"画笔手势 → 矢量选区 → 几何/样式命令"这个三段式结构是合理的，应作为所有修复工具的共同基础。** 现有 Editor V0.1 的编辑核心已经是"命令 + 撤销 + 保存校验"的形状，只差把选区独立出来。
5. **最值得先做的两个最小 POC：** ① 区域刷选面 + 预览 + 受控合并（直接针对已测出的最大人工成本）；② 几何与样式分离的 Legend 字段 + 线型重绘（不改几何，只加样式表）。

## 1. 对新产品理念的评价

**同意的部分：**
- 不再用更复杂的识别去追最后几个百分点。之前多轮实验（D71、B1、B2b、颜色检查）都显示，局部指标改进常伴随新的误检或对象膨胀【已证明，见历次报告】。
- 用户给出一次意图（"这片是同一个地层"）替代大量不确定的自动推断，这在编辑实测里已有证据：PN2 选一个组、改两个属性就修好了，而识别侧要把它做对需要新的检测规则【已证明，`editor_v01_uat.md`】。
- 几何与样式分离：现在的 GPKG 里颜色、线宽是对象属性，样式没有独立存储，切换图例只能逐个改属性【已证明，看 `core.py` 和 GPKG 字段】。

**需要修正的部分：**

1. **"先达到 97% 才能做后续"本来就不是前提**，这点同意。但识别侧有一个缺陷是编辑器无法便宜地补救的：交叉处的线身份（Checkpoint A：合成图 409 个近邻漏检是交叉歧义）。这类错误在编辑器里表现为"一条线在交叉处断开或接到了另一条线上"，修起来要拆分再连接。智能连线可以降低成本，但不能完全替代。
2. **线条笔画污染面层，在 B2c 上已不是主要的碎面来源。** 本轮只读检查 u2（地图区 94×300 px，原图 8,810 种 RGB）：

   | 版本 | 面数 | ≤ 5 px² 的小面 | 其中离某条线 线宽/2+2 px 以内 |
   |---|---|---|---|
   | F0（只有面，不分线） | 1,933 | 1,859 | 1,434（77%） |
   | B2c（线面分层） | 665 | 610 | 185（30%） |

   F0 的碎面四分之三贴着线，B2c 已经通过"线下用邻近颜色填补"去掉了大部分【已证明，本轮计算】。B2c 剩下的 610 个小面中有 425 个不在任何已识别线附近，更可能来自颜色量化、抗锯齿、文字和花纹。
   用户看到的"深绿色斜线旁的碎面"，可能是那条线**没有被识别成线**，于是它的笔画仍在面层里。这一点需要一个小实验确认（见第 9 节 POC 0）。
3. **Legend 重绘解决的是"画出来像图例"，不解决"几何对不对"。** 一条断层如果位置偏了 3 px 或在交叉处断了，套上标准线型后会更好看，但依然是错的。两者要分开验收。

### 3.2 与绣娘相关的模块

| 模块 | 依赖 | 实际做什么 | 对绣娘的价值 |
|---|---|---|---|
| `algo/src/selection/`（`lasso.rs`、`marquee.rs`、`morphology`、`distance`、`inverse`、`combine_mask`） | `geom`、`color`、`raster`、`rustfft` | 选区是栅格覆盖率蒙版（每像素 0–1），套索把多边形栅格化成蒙版，按瓦片计算；扩大缩小、羽化、反选、相加相减都作用在蒙版上 | **借鉴设计**：选区运算的种类（加、减、交、扩、缩、反选）和"选区独立于工具"的思想。代码本身输出像素蒙版，绣娘要的是 Feature ID 集合，**不值得移植** |

| `vector/`（`stroke.rs`、`edit.rs`、`trace.rs`、`flatten.rs`、`feather.rs`） | `geom`、`color`、`raster`、`doc` | 路径锚点、曲率节点、命中测试（`hit`）、描边生成多边形（`stroke_polygons`）、虚线切分（`dash_polyline`）、蒙版描摹成路径（`trace_mask`、`fit_trace`） | **最接近可用**：节点编辑和 `dash_polyline` 的逻辑对 Legend 线型重绘和路径修正有参考价值。但它依赖 `doc` 和 `raster`，**不是零依赖的独立库** |
| `doc/src/pattern.rs`（249 行） | — | 图案是一块栅格瓦片（`Surface`），按平铺方式填充 | **只借鉴参数**（缩放、偏移、角度）。绣娘的图案必须是矢量（或至少可在 GIS 中用符号表达），**不能直接用** |
| `engine/` | 几乎所有其他 crate | 命令规格：每个操作是带 ID、名称、菜单、快捷键、参数、启用条件的命令，注册到统一表里，供菜单、快捷键、脚本和自动化（MCP）调用；书中说明权限控制"尚为提案" | **借鉴设计**：命令注册表 + 统一入口。代码体量 16 万行，与像素文档模型强绑定，**不值得移植** |

### 3.3 关键差异

PhotoCraft 的所有编辑最终落在**像素文档**上；绣娘的编辑必须落在**带共享边界的矢量面和带属性的线**上，并且保存后能通过拓扑检查。这意味着：
- PhotoCraft 的选区回答"哪些像素"，绣娘要回答"哪些 Feature"。
- PhotoCraft 的修复画笔回答"像素应该变成什么颜色"，绣娘要回答"哪些面应该合并到哪个面、边界怎么走"。
- PhotoCraft 没有拓扑校验，也不需要。

所以第 6 节那一层（手势 → 矢量选区 → 命令）**在 PhotoCraft 里没有可移植的对应实现**【PhotoCraft 源码阅读结论】。

## 4. 三条迁移路线比较

| 项 | A 保留现有编辑器，借鉴 PhotoCraft | B 定向移植 Rust 模块 | C Fork PhotoCraft |
|---|---|---|---|
| 技术栈 | Python + Shapely + GPKG 核心，HTML/JS Canvas 前端（现状） | A 之上加 Rust 扩展（PyO3）或 WebAssembly | Rust + egui + wgpu 桌面程序 |
| 能复用的现有成果 | 编辑核心、撤销重做、保存校验、浏览器测试全部保留【已证明】 | 同 A | 现有编辑器基本全部放弃；Python 识别流水线需要通过文件交换衔接 |
| 需要新写的 | 选区系统、图例样式、渲染器、左右对照、修复刷 | 同 A，再加跨语言桥接和构建链 | GPKG 读写、属性模型、拓扑校验、图例系统，全部在 Rust 中重写；还要理解 16 万行 engine 和 28 万行 UI 才能改 |
| 可移植性风险 | 低：只借鉴设计 | 中：所选模块依赖 `geom`、`raster`、`color`、`doc`，输入输出是像素 `Surface`，不是独立库【源码阅读】 | 高：像素文档模型与矢量拓扑模型根本不同 |
| 维护成本 | 低 | 中：两种语言、两套构建 | 高：跟随上游需要不断合并；不跟随则等于自己维护一个巨大分支 |
| 许可证 | 无问题（只借鉴） | 需保留 MIT/Apache 声明，审查被移植代码的依赖 | 需完整审查全部依赖和 `craft-libs` |
| 粗略工作量（估计，不是承诺） | 选区 + 刷选面 POC 约 1–2 周；Legend 最小版约 2–3 周 | A 的工作量再加 1–3 周桥接，且只有在 A 出现性能瓶颈时才有收益 | 达到 Editor V0.1 同等功能估计 2–3 个月以上 |

**判断：选 A。** 你们的倾向是合理的。B 只在第 10 节所说的性能边界被实际撞到时才值得做；C 的代价主要花在与绣娘无关的像素编辑能力上。

## 5. Legend 重绘系统的最小架构【设想】

**原则：几何和样式分开存。改样式不动任何顶点。**

在 GPKG 中增加两张普通属性表（GPKG 允许没有几何的表，GIS 软件都能读）：

| 表 | 字段 | 说明 |
|---|---|---|
| `legend_styles`（这张图的图例表） | `legend_id`、`name`、`code`、`kind`（line / face）、`colour`、`width_px`、`pattern`（JSON，见下）、`source`（from_legend / user）、`version` | 每张地图一份，初稿可由 `legend_swatches` 自动生成，用户修改 |
| 对象绑定 | 在 `colour_faces`、`visual_lines` 上加 `legend_id`、`line_role`（`overlay` / `boundary` / `unknown`）、`style_override`（可选 JSON） | 一个对象只绑一个图例；切换图例只改这个字段 |

**线型参数（`pattern` JSON 示例）：**

```json
{"stroke": {"dash": [6, 3], "width_px": 2},
 "marks": [{"shape": "triangle", "size_px": 5, "spacing_px": 20, "side": "left", "offset_px": 0}]}
```

覆盖实线、虚线、点划线和"沿线重复符号"（断层齿、短划线）。渲染时沿 LineString 按弧长放置符号，方向取局部切线。PhotoCraft 的 `dash_polyline` 可以作为虚线切分的参考实现。

**面填充参数：**

```json
{"fill": "#d3e5a1", "hatch": [{"angle_deg": 45, "spacing_px": 8, "width_px": 1, "colour": "#557733"}],
 "dots": {"spacing_px": 10, "radius_px": 1}}
```

先只支持"底色 + 平行线 + 点阵"三种，它们覆盖地质图中大部分面花纹，并且都能在 QGIS 中用"线状填充""点阵填充"符号原生表达。

**两层图例：**
- 通用图例库：线型和花纹的模板（例如"正断层""逆断层""第四系点纹"），跨图复用。
- 当前地图图例表：引用模板，但颜色、间距按这张图的实际印刷调整。不假设不同地质图用相同配色。

**导出：**
- GPKG 主体始终是干净的几何和属性，样式另存为表；其他 GIS 软件至少能读到几何、`legend_id` 和颜色。
- 另外生成一份 QGIS 样式文件（QML），让 QGIS 打开时按图例显示。生成 QML 不需要改几何。

**不做：** 自动识别每一种图例。用户点一下"指定图例"就够了；自动建议（`s1_semantic` 的 A2c / A2t）只作为默认选项。

## 6. 核心架构：画笔手势 → 矢量选区 → 几何/样式命令

这是绣娘与 Photoshop 最大的区别，也是最该自己做的部分。我认为这个分层合理，并建议所有修复工具都建在它上面。

```
手势（像素坐标）         选区（Feature ID 集合）           命令（事务）
画笔轨迹 + 半径     →    select(layer, region, rule)  →  ApplyLegend / MergeFaces / HealFragments ...
套索多边形               + 加 / 减 / 交                   预览 → 确认 → 执行 → 校验 → 记录
魔棒种子点               + 扩展 / 收缩（按邻接）           撤销 / 重做 / 重放
```

**第一段：手势只是几何。** 画笔轨迹 = 折线缓冲成多边形；套索 = 多边形；魔棒 = 在原图上按颜色连通得到的像素区域，再转成多边形。全部用 Shapely 表达。

**第二段：选区是"Feature ID 集合"，而不是蒙版。** 选区规则只有几种，可以组合：
- 与手势多边形相交 / 中心点在内 / 被覆盖面积 ≥ x%
- 只选某一层（面、线）
- 只选面积 ≤ x px² 的面
- 按邻接关系向外扩一圈、向内缩一圈
- 用原图约束：只保留颜色与目标相近的像素多的面

选区运算（加、减、交）就是集合运算。选区本身不修改任何数据，可以随时显示、剔除个别对象。

**第三段：命令是事务。** 每个命令接收"选区 + 参数"，先生成**预览**（会改哪些对象、改成什么、新的边界在哪），确认后执行、校验（严格覆盖检查）、写日志。失败整步回滚。

**现有代码里已经有的【已证明】：**
- `core.py` 的每个编辑都是 `_do(desc, fn)`：先快照、执行、失败回滚、记录日志、可撤销重做。
- `pick`、`box`、`group`、`adjacent_similar` 已经是"返回 Feature ID 列表"的选区函数。
- 保存时自动回读并做严格覆盖检查。

**缺少的：** 独立的选区对象（现在选区只存在于前端变量里）、选区运算、预览接口、画笔和套索手势、命令注册表（让鼠标、快捷键、脚本、Agent 调同一个命令）。

**命令注册表借鉴 PhotoCraft 的做法：** 每个命令有 ID、参数说明、启用条件。绣娘里可以是一个 Python 字典，HTTP 接口按命令 ID 分发，脚本直接调用同一函数。这样第 9 节的验收脚本、浏览器测试和未来的 Agent 都走同一入口。

## 7. 智能修复刷【设想】

**输入：** 用户刷过的区域（手势多边形）+ 用户指定的目标（一个图例，或"并入周围的面"）。

**步骤：**
1. 选区：刷过区域内、面积 ≤ 阈值的面为候选。
2. 对每个候选面决定去向，只用局部信息：
   - 与之共享边界最长的非候选面（"邻居"）
   - 该面在原图中的像素颜色与邻居颜色的差
   - 是否被某条已识别的线覆盖（在线宽 + 1 px 内）
3. 分类：
   - **并入邻居**：被线覆盖，或颜色与邻居相近
   - **保留**：颜色与所有邻居都明显不同，且面积达到最小值（可能是真实小地质体）
   - **待确认**：其余情况，高亮给用户看
4. 预览：显示合并后的新边界和每个面的去向，用户可以点击改判。
5. 执行：按邻居分组做合并（现有 `merge_faces`），再应用目标图例。

**防误删：** 不只看面积；颜色明显不同的一律不自动并；只作用于刷过的区域；必须预览；可以撤销。

**已有依据：** 碎面实验里，37 个碎面中有 1 个与其他面不相邻，`merge_faces` 正确拒绝了；合并后有 276 px² 越过真实边界【已证明】。这说明修复刷必须在预览里显示越界面积，而不能只显示"合并了几个面"。

## 8. 套索、魔棒、样式吸管、智能连线如何共用基础

| 工具 | 手势 | 选区规则 | 命令 |
|---|---|---|---|
| 颜色刷 / 图例刷 | 画笔轨迹 | 与轨迹相交的面（或线） | `ApplyStyle` |
| 套索 | 多边形 | 中心点在内的面 | 任意（合并、改样式） |
| 魔棒 | 原图种子点 | 原图同色连通区域覆盖 ≥ 50% 的面 | 任意 |
| 样式吸管 | 点击一个对象 | 该对象 | 读取样式，存为当前画笔样式 |
| 碎面修复刷 | 画笔轨迹 | 轨迹内的小面 | `HealFragments`（见第 7 节） |
| 智能连线 | 两个端点 | 两条线 | `ConnectLines`：按端点方向生成连接段，预览后写入；原图局部线迹只作为评分参考 |
| 节点编辑 | 拖动 | 一条线的一个顶点 | `MoveVertex` |

除了智能连线和节点编辑需要新的几何算法，其余工具都只是"手势 + 选区规则 + 已有命令"的组合。**共同基础是三样东西：手势转多边形、选区对象及其运算、命令注册表加预览。** 先做这三样，后面每个工具都只是几十行配置。

## 9. 最值得开展的最小 POC

**POC 0（半天，只读）：确认"斜线旁碎面"的来源。** 在用户截图的位置，检查那条深绿色斜线是否在 `visual_lines` 里。如果不在，碎面就是笔画留在面层里（识别漏线）；如果在，再看碎面是否在线宽内（线下填补没盖住）或在线宽外（量化 / 抗锯齿）。只读，不改算法。

**POC 1：区域刷选面 + 预览 + 受控合并。**
- 内容：选区对象（加 / 减 / 按邻接扩缩），画笔和套索手势，合并预览（显示新边界和越界面积），确认后执行。
- 验证：用碎面实验的同一区域（合成图 7001 绿色区域，37 个碎面）。目标是从"逐个点 37 次"降到"刷 1–3 下 + 剔除几个"，越界面积在预览中可见。
- 为什么先做它：编辑实测中最大的人工成本就在这里【已证明】。

**POC 2：几何与样式分离的 Legend 字段 + 线型重绘。**
- 内容：在 GPKG 增加 `legend_styles` 表和 `legend_id`、`line_role` 字段；编辑器能把一个图例应用到选中的线或面；渲染虚线、点划线、沿线三角齿和面的平行线花纹；导出一份 QML。
- 验证：u2 中的断层线套用"断层 + 齿"样式后，GPKG 几何逐顶点不变；QGIS 中按 QML 显示（这一步需要先装 QGIS，否则标记 `NOT_VERIFIED`）。

POC 1、2 彼此独立，可以并行。

## 10. 性能与大图幅

**现状【已证明】：** `/api/state` 每次返回所有面和线的完整坐标 JSON；前端每次重画所有对象；u2（665 面、35 线）和合成图（398 面）很流畅。

**预计的边界【设想，未测】：**
- 当对象达到数万、坐标点达到数百万时，全量 JSON 和全量重绘会成为瓶颈。
- 对策按顺序：① 后端用 Shapely STRtree 做空间查询，前端只请求可见范围；② 只把修改过的对象发回前端；③ 静态面层画到离屏缓存，只重画选区和修改部分；④ 仍不够时改用 WebGL。
- 选区计算放在后端：Shapely 的向量化谓词（`intersects`、`contains_xy`）配合 STRtree，十万级对象的局部查询通常在毫秒到百毫秒级；画笔一笔只查一次。
- 撤销现在是整层快照（`copy()`），大图时内存会随步数线性增长。需要改成只记录被修改对象的前后状态。
- **Rust 何时真正有优势：** 当单个命令需要在大范围内做大量逐对象几何运算，并且向量化的 Shapely 仍然太慢时。在那之前，瓶颈更可能在数据传输和前端绘制，Rust 帮不上。

## 11. 对十个问题的回答

1. **保留 StitchVector 3.0、重点转向 Legend 和编辑？** 同意。补充：交叉处的线身份仍是编辑器难以便宜补救的问题，应保留一项最小的识别改进或对应的连线工具。
2. **哪些可以直接复用？** 图例色块检测、图例 OCR、区域到代号的建议（第 2 节）。缺的是样式数据结构、渲染器、`legend_id` 和 `line_role` 字段。
3. **笔画污染是否是碎面主因？** 在 F0 上是（77% 的小面贴着线），在 B2c 上已不是（30%）。B2c 剩下的小面多数离已识别的线较远。用 POC 0 半天就能确认截图中的具体情况。
4. **PhotoCraft 哪些可借鉴？** 设计可借鉴：选区运算种类、命令注册表、节点编辑交互、虚线切分。值得考虑移植的只有 `vector` 中少量路径函数，但它依赖 `doc`、`raster`，不是独立库。选区、画笔、修复、图案都工作在像素上，与 GIS 编辑差异太大。
5. **Python 还是 Rust？** 保留 Python + Shapely。性能分界点在"单次命令的大范围逐对象几何运算"，目前离这个边界很远；先做空间索引和增量传输。
6. **Legend 数据结构？** 见第 5 节：独立图例表 + 对象上的 `legend_id`，切换图例只改一个字段。
7. **智能修复刷？** 见第 7 节：局部、按邻居分组、颜色明显不同的不自动并、必须预览。
8. **工具如何组合？** 见第 8 节：手势 → 选区 → 命令三段式，共同基础是手势转多边形、选区对象、命令注册表。
9. **Editor V0.1 保留什么？** 保留 `core.py` 的编辑核心、撤销、保存校验，以及服务和测试。需要改的：选区移到后端成为对象；撤销改为增量；新增命令注册表；前端拆成两个同步视图（左原图、右矢量）。不需要换前端框架：目前只有约 130 行 JS，加左右视图和画笔后也在原生 JS 可控范围内。等到超过约 1,500 行或需要复杂面板时，再考虑引入轻量框架。
10. **最有价值的三项编辑能力？**
    - **区域刷选 + 受控合并**：碎面实验中选择成本最高（37 次点击），且直接决定面层能否交付。
    - **逻辑组的样式与线宽操作（含图例套用）**：PN2 只用约 5 步就修好，说明这类操作成本最低、收益最直接。
    - **智能连线**：Checkpoint A 中交叉歧义是最大的线问题，而 PN1 的修复步骤里拆分和补画占了大半。

## 12. 如何验证人工工时真的减少

- **基准：** 选一个已授权的真实样区，先记录一位熟练用户纯手工矢量化所需时间（或用历史项目的实际工时）。
- **对比：** 同一用户用"自动结果 + 编辑器"完成同一样区，到通过同一验收标准为止。
- **记录：** 编辑器已经写出每一步的修改日志（`*.edits.json`），可以直接统计操作次数和每类操作的时间戳；再加一个计时器记录总时长。
- **验收标准要先定好**（例如几何偏差、拓扑有效、图例正确），否则省下的时间可能只是"标准降低了"。
- 一张图的结果不能外推到全部地图，需要至少几种不同类型的图幅。
