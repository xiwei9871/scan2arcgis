## 0. 结论

**整条自动链路可以工作：两种线层（B0 / B2c）接入现有面层后，GPKG 回读与内存合成逐像素一致，所有面层通过严格拓扑检查，没有空洞，编辑一组线不影响任何无关对象。B2c 比 B0 多恢复淡色线，面数和顶点数更少，其他指标持平。**

但最终画面有三个明确问题，来源不同：

| 问题 | 来源 | 影响 |
|---|---|---|
| 1. 线附近颜色变差（dE90 21 → 35） | 线的表示方式：一条线一种颜色、一个宽度 | 线本身更连续，但抗锯齿深浅丢失；Oracle 阶段已知 |
| 2. 合成图中 2 条黄色窄带（3 px、5 px）完全消失 | **面层**：合并后的面颜色表里没有这两条带的颜色（最近的颜色差 15.6 / 26.1 dE） | 只有面、不加线时也同样消失，与描线无关 |
| 3. 反例场景中的窄色带变成了"线对象" | **描线**：色带颜色没有大面积出现，不被识别为填色，于是被描成线（带轴线 98% 被线覆盖） | 颜色看上去保住了，但在 GPKG 里是线而不是面，编辑时会被当作线 |

**是否进入真实地图验证：** 建议进入，但只在已经授权的 u2 中心 300×300 上做一次，与 Oracle v2（同一样区、人工线稿）直接对比。合成数据已经说明链路可用、问题出在哪里；继续在合成图上调整意义不大。上面第 2、3 条会带到真实图上，预期会出现，应作为观察重点，而不是事先修补。

## 2. 测试结果（合成图 7001–7005，所有图都是 GPKG 回读）

### 2.1 视觉还原

| 方案 | 全图 dE90 | 线邻域 dE90 | 非线区域 dE90 | dE ≤ 10 的像素比例 |
|---|---|---|---|---|
| F0 只有面 | 10.51 | 21.10 | 6.03 | 0.895 |
| B0 线 + 面 | 10.61 | 34.96 | 6.03 | 0.897 |
| B2c 线 + 面 | 10.50 | 34.98 | 6.03 | 0.898 |

沿真值线的颜色存在率（回读颜色与原图差 ≤ 15 dE 的比例）：

| 线 | F0 | B0 | B2c |
|---|---|---|---|
| 淡色 1 px | 0.64 | 0.57 | **0.71** |
| 红 2 px | 0.57 | 0.77 | 0.77 |
| 红 3 px | 0.74 | 0.86 | 0.86 |
| 渐宽 2→5 px | 0.84 | 0.87 | 0.87 |
| 与同色填色面相接 | 0.64 | 0.76 | 0.76 |
| 黑 1 px | 0.54 | 0.47 | 0.47 |
| 黑 3 px | 0.93 | 0.89 | 0.89 |
| 黑 5 px | 0.96 | 0.92 | 0.92 |

- 红线、渐宽线、同色填色面上的线：加线层后明显更好。
- 黑线：加线层后略差。黑线在面层里本来就有自己的颜色类，单色线条覆盖后抗锯齿深浅丢失。
- 淡色线：B0 线层反而比只有面略差（线条被描成不准的颜色，盖住了面层的颜色），B2c 多找回的淡色线让它超过 F0。

反例场景（7101–7105）墨线存在率：

| 子类型 | F0 | B0 | B2c |
|---|---|---|---|
| 深色墨线 | 0.01 | 0.92 | 0.92 |
| 深色墨线沿填色边界 | 0.00 | 0.99 | 0.99 |
| 淡色墨线（比两侧暗） | 0.74 | 0.89 | **0.97** |
| 淡色墨线沿填色边界 | 0.39 | 0.60 | **0.82** |

### 2.2 线面正确性

| 项 | F0 | B0 | B2c |
|---|---|---|---|
| 所有面层严格拓扑有效（合成 + 场景，共 30 个文件） | 是 | 是 | 是 |
| 未覆盖像素 | 0 | 0 | 0 |
| 内存合成与 GPKG 回读的差异像素 | 0 | 0 | 0 |
| 误检线长度 px（填色边缘 / 色带 / 其他） | — | 132 / 75 / 11 | 145 / 75 / 11 |

窄色带（合成图，`colour_preserved` = 色带中心回读颜色与原色差 ≤ 15 dE 的比例；`axis_under_line` = 色带轴线被线层覆盖的比例）：

| 色带 | F0 保色 | B2c 保色 | B2c 被线覆盖 |
|---|---|---|---|
| 7001 绿 / 黄 | 0.72 / 0.65 | 0.76 / 0.67 | 0.14 / 0.26 |
| 7002 绿 / **黄 5 px** | 0.79 / **0.00** | 0.81 / **0.00** | 0.16 / 0.16 |
| 7003 绿 / **黄 3 px** | 0.80 / **0.00** | 0.80 / **0.00** | 0.06 / 0.04 |
| 7004 绿 / 黄 | 0.88 / 0.68 | 0.89 / 0.68 | 0.04 / 0.23 |
| 7005 绿 / 黄 | 0.98 / 0.64 | 0.98 / 0.65 | 0.00 / 0.22 |

两条失败的黄带在只有面时也完全消失，原因是面层颜色表里没有这种黄色（`lf_test_band_check.json`：最近颜色差 26.1 dE 和 15.6 dE；对照 7001 的黄带最近颜色差 2.9 dE，保住了）。这是**面层的颜色归并问题**：32 色量化后再按 dE < 10 合并，窄带的颜色像素太少，被并入其他颜色。

反例场景中的色带：保色比例 F0 0.979、B0 / B2c 0.976（最低 0.68），但 B0 / B2c 中色带轴线 98% 被线层覆盖，F0 为 0。也就是说，加线层后色带的颜色看上去基本还在，但是**以线对象的形式存在**。这是**描线问题**，与 B2c 无关（B0 相同）。

### 2.3 编辑性

| 项 | F0 | B0 | B2c |
|---|---|---|---|
| 面对象 | 8,387 | 2,305 | 2,123 |
| 线对象 / 逻辑组 | 0 | 179 / 138 | 199 / 148 |
| 总顶点 | 69,589 | 35,115 | 33,571 |

- 线面分层让面数减少约 75%，顶点减少约 52%。
- GPKG 编辑检查（每张图取最大的一个逻辑组，改色、下移 3 px，重新回读）：B0 和 B2c 的 10 次编辑中，**被编辑组以外的像素变化全部为 0**。`logical_id` 写入后完整保留。
- QGIS 图形界面编辑：`NOT_VERIFIED`（本机没有 QGIS）。GPKG 是像素坐标、无 CRS，在 QGIS 中会显示为未定义坐标系。

## 3. 问题归因

| 现象 | 描线 | 面层 | 组合 |
|---|---|---|---|
| 线附近颜色变差 | | | ✓ 单色线覆盖抗锯齿区域 |
| 黄带在面层中消失 | | ✓ 颜色归并丢掉窄带颜色 | |
| 色带被描成线 | ✓ 色带颜色未被识别为填色 | | |
| 淡色线 B0 比只有面更差 | ✓ 线颜色测得不准 | | ✓ |
| 填色边缘误检线 | ✓（B2c 新增 13 px） | | |

## 4. 建议

1. **进入真实地图验证**：只用已授权的 u2 中心 300×300，F0 / B0 / B2c 三种自动方案，与 Oracle v2（人工线稿）对比，同样从 GPKG 回读。目的是看真实图上上面三类问题的实际严重程度。
2. **不在合成图上继续修补。** 如果真实图上窄带问题确实严重，再单独讨论一个最小修复（例如面层颜色表保留小面积但颜色独立的类别），一次只改一处。
3. B0 仍是默认，B2c 仍是候选。B2c 在本轮没有带来任何退化，又在淡色线和面数上有收益，真实图验证可以把它作为主方案。
